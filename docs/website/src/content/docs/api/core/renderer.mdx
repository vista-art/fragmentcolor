## Description

The [Renderer](/api/core/renderer) is the main entry point for
[FragmentColor](https://fragmentcolor.org) and normally the first object you create.

It is used to render
[Shaders](/api/core/shader) and
[Passes](/api/core/pass) (single passes or any iterable of them)
to a [Target](/api/targets/target) (canvas, window, or texture).

The [Renderer](/api/core/renderer) internals are lazily initialized
when the user creates a [Target](/api/targets/target).

See the constructor [Renderer::new()](/api/core/renderer#new)
description below for details.

### Renderer::create_depth_texture \{#create_depth_texture\}

Create a depth texture using `Depth32Float`.

A pass that draws models gets a depth buffer without one. Create a depth texture to read depth in a later pass, or to give depth to a pass of plain meshes.

A width or height of zero, a side past the device limit, or a depth other than 1 is an error, the one `resize` returns: `TextureError::InvalidInput` inside `InitializationError::TextureError` in Rust.

The created depth texture inherits the renderer's current sample count:
- If you called `create_target(window)` (surface-backed), it matches the negotiated MSAA (e.g., 2×/4×) for that surface.
- If you are rendering offscreen via `create_texture_target`, it defaults to 1.

This ensures the depth attachment `sample_count` matches the pass sample count.
A depth texture with a different `sample_count` than the pass makes `render` return
`RendererError::DepthSampleCountMismatch`, and one whose width or height differs from
the pass's color attachment returns `RendererError::DepthSizeMismatch`, before it takes
a frame. A window that resizes needs a depth texture of the new size, or a `resize` of this one.

### Renderer::create_external_texture(source) \{#create_external_texture\}

Wrap a native platform video-frame source as an external texture so a WGSL
shader can sample it directly via `texture_external` /
`textureSampleBaseClampToEdge`, without an intermediate CPU upload.

The method exists on the Web, iOS and Android bindings. Desktop Rust and
Python have no native video-frame source to pass, so they don't have it.
The `source` argument is platform-specific:

- **Web**: `HTMLVideoElement` (or anything that decodes into one).
- **iOS**: a raw `UInt64` pointer to a `CVPixelBuffer`.
- **Android**: a raw `ULong` pointer to a `SurfaceTexture`.

Every call returns an error for now. The signature is stable, and the
native decode hookup is on the roadmap. Track support via the typed
`RendererError` you get back.

### Renderer::create_storage_texture \{#create_storage_texture\}

Create a storage-class texture for compute shaders, image store/load, or as a render target.

Common forms:

- `(size, format)`: empty storage texture, no initial data.
- `(size, format, bytes)`: storage texture pre-seeded with `bytes`, exactly the size's pixel count times the format's bytes per pixel.
- A full `TextureInput { data, options }` literal: pass `options.usage` (via `TextureOptions::with_usage(...)`) for non-default usage flags.

`size` is required; storage textures have no source to infer dimensions from. Missing it returns `RendererError::CreateTextureError`.

A depth of 1, or none, makes a 2D texture, and a larger depth makes a 3D texture. A side of zero, or a size past the device's limits for that kind of texture, is an error that reaches no GPU call: `TextureError::InvalidInput` inside `RendererError::TextureError` in Rust, a thrown `Error` in JavaScript, `InvalidInputError` (a `FragmentColorError`) in Python, `FragmentColorError` in Swift and `FragmentColorException` in Kotlin.

`options.usage` overrides the default mask of `STORAGE_BINDING | TEXTURE_BINDING | COPY_SRC | COPY_DST`. Every binding has the same named `TextureUsage` flags, combined with `|` (`or` in Kotlin). The other bindings take the size, format, optional bytes and optional usage as separate arguments. An empty mask, or a bit outside the five `TextureUsage` flags, is the same `InvalidInput` error. So is a usage the format can't take on this device, such as `STORAGE_BINDING` on `Depth32Float` or `Rgba8UnormSrgb`, and a depth texture with a depth past 1.

### Renderer::create_texture \{#create_texture\}

Create a [Texture](/api/texture/texture) from bytes, a file path, a URL, a KTX2 container, or a pre-built [Mipmap](/api/texture/mipmap).

When you pass a `size`, the bytes are treated as raw pixels in the chosen format. Without a size, the bytes (or the file/URL contents) are decoded as PNG, JPEG, BMP, HDR, etc. A size applies to bytes only: a path, a URL, a KTX2 file and a `Mipmap` carry their own, so a size with one is an `InvalidInput` error, raised before any file read or fetch.

A size with a side of zero, or one past the device's limits, is an error that reaches no GPU call, and so is an image larger than the device takes, which is checked from its header before the pixels decode: `TextureError::InvalidInput` inside `RendererError::TextureError` in Rust, a thrown `Error` in JavaScript, `InvalidInputError` (a `FragmentColorError`) in Python, `FragmentColorError` in Swift and `FragmentColorException` in Kotlin.

Decode and mipmap generation run on a background worker on native platforms. On the web they run inline on the caller's thread; move heavy decode into a Web Worker if you need parallelism.

#### Per-language shapes

- **Rust:** `create_texture(input)`. `input` accepts bare bytes, `(bytes, [w, h])`, `(bytes, format)`, `(bytes, options)`, a path, a URL string, a `Texture`, a `Mipmap`, or a KTX2 input. A string that starts with `http://` or `https://` is a URL; any other string is a path.
- **JS:** `await renderer.createTexture(input, options?)`. `input` is `Uint8Array` / `ArrayBuffer` / URL string / CSS selector / `HTMLImageElement` / `HTMLCanvasElement` / `OffscreenCanvas` / `ImageData` / a `Texture` / a `Mipmap`. `options` is `{ size?, format?, mipmaps?, sampler?, usage? }`; when `size` is set, `input` is read as raw pixel bytes. `ImageData` and canvases bring their own size and RGBA pixels, so their options may repeat that size and pick an 8-bit RGBA or BGRA format, and anything else throws. The options object takes the size under `size`, and a `width` or `height` beside another option throws.
- **Python:** `renderer.create_texture(input, size=None, format=None, mipmaps=None, sampler=None, usage=None)`. `input` is `bytes` / `bytearray` / `memoryview` / a list or tuple of ints / a path or URL `str` / `os.PathLike` / uint8 numpy `ndarray[H, W, C]` / `Texture` / `Mipmap`. Numpy arrays fill in `size` for you, and a `size` that differs from the array's raises `InvalidInputError`. An array is raw bytes in the named format: one whose channels match the format's bytes per pixel uploads as it is, such as an `(H, W)` array as `R8Unorm` or a 4-channel array as `Bgra8Unorm` with no swap, and one with 1 or 3 channels gains an opaque alpha for an 8-bit RGBA or BGRA format. Any other shape raises `InvalidInputError`.
- **Swift / Kotlin:** `try await renderer.createTexture(bytes)`, `createTexture(bytes, format)`, `createTexture(bytes, [w, h])`, `createTexture(bytes, options)`, `createTexture(path)` or `createTexture(chain)`. Bytes are `Data` or `[UInt8]` in Swift and `ByteArray` in Kotlin. Every bytes form also takes an optional `usage`.

#### How the discriminator works

| Form | Treatment |
|------|-----------|
| `bytes` (no size) | Encoded image; decoded internally (PNG, JPEG, BMP, HDR, etc.). |
| `(bytes, size)` / options with `size` set | Raw pixel bytes; exactly `bpp(format) * width * height * depth` long, no decode, and any other length is an `InvalidInput` error. The default `Rgba` format uploads them as linear `Rgba8Unorm`. |
| `(bytes, format)` / options with `format` set | Encoded image reinterpreted as `format` (e.g. `Rgba8Unorm` for normal-map data, `R16Unorm` for 16-bit grayscale, `Rgba32Float` for full float precision). |
| `path` / `URL` | File or HTTP fetch, then decoded. A size with it is an error. |
| `Mipmap` | Pre-built CPU mip chain; GPU-only upload. Build via [Mipmap::build](/api/texture/mipmap#build) on a worker thread. |
| `Ktx2Bytes` / `Ktx2Path` / `Ktx2Url` | KTX2 container (BC / ETC2 / ASTC / uncompressed); the file's declared format and pre-baked mip chain win. |

A full mipmap chain is generated by default (`options.mipmaps = true`), for source images and for raw bytes in a color or float format, float data included. Set to `false` to skip the CPU work for textures that won't be sampled at distance, and for any texture you update in parts with `write_region`, which refuses a partial write into a chain. Raw bytes upload as given at level 0, and the levels below it are resampled from them.

An HDR image decodes into `Rgba16Float`. A value past the half float range saturates at 65504, or -65504, and never becomes infinity, the way Three.js converts it. An explicit `Rgba32Float` keeps the full range, and a linear sampler filters it where the device has `FLOAT32_FILTERABLE`. Every mip level of a float texture averages the f32 values of the level above it with a box filter, so values below 0 and above 1 keep their size at every level. For `Rgba16Float` those are the values before the level is stored as half floats, and only storing a level saturates it.

A decoded image, an `ImageData` or a canvas holds RGBA by definition, so it uploads into `Bgra8Unorm` blue first and its colors sample right. Every path that takes an `ImageData` or a canvas does this: `createTexture`, the Material texture setters, `Texture.write` and `writeRegion`, `Mipmap.build` and the `createStorageTexture` seed. Raw bytes, a NumPy array among them, are texels in the named format and upload as given, never swapped. A decoded image fills the 8-bit and 16-bit color formats and `Rgba16Float` or `Rgba32Float`. An integer format such as `Rgba32Uint`, or `Depth32Float`, is an `InvalidInput` error: pass raw bytes with a size for an integer texture, and draw into a depth texture.

`options.usage` adds `TextureUsage` flags to the `TEXTURE_BINDING | COPY_DST` every texture made from data has, such as `COPY_SRC` to read it back. A bit outside the five `TextureUsage` flags is an `InvalidInput` error.

### Renderer::create_texture_target(size: [u32; 2]) \{#create_texture_target\}

Render to an offscreen texture without a Window or Canvas.

This is useful for tests, server-side rendering, or running examples in CI.

A width or height of zero, a side past the device limit, or a depth other than 1 is an error, the one `resize` returns: `TextureError::InvalidInput` inside `InitializationError::TextureError` in Rust, a thrown `Error` in JavaScript, `InvalidInputError` (a `FragmentColorError`) in Python, `FragmentColorError` in Swift and `FragmentColorException` in Kotlin.

### Renderer::load \{#load\}

Realize every pending GPU upload referenced by a renderable. Material's
texture setters (`base_color_texture`, `metallic_roughness_texture`, …)
accept paths, bytes, and URLs in addition to
already-uploaded [`Texture`](/api/texture/texture)
handles; the path / bytes / URL variants are stored on the Material's
Shader as *pending* uploads. `load` walks every Shader the renderable
visits, drains its pending list, calls
[`Renderer::create_texture`](/api/core/renderer#create_texture)
for each, and writes the resulting `Texture` into the matching uniform.

An upload that fails stays pending and the others still bind, so a good
normal map binds even when the base color path is missing. `load` returns
the first failure, and so does every later `load`, and every native
`render`, until the input is fixed or replaced. The latest setter call for
a map wins, so setting a map again replaces the pending upload.

On native targets, [`Renderer::render`](/api/core/renderer)
runs `load` first whenever the renderable has pending uploads, so an
explicit `load` is optional there. Reach for it when you want to pay the
decode and upload cost outside the render loop, for example in a loading
screen that prepares the scene before the first frame goes out.

On the web, `render` can't wait for an upload, so it leaves pending uploads
alone. Await `load` before the first `render`. Until then, a PBR Material
draws with its 1×1 default maps.

In JavaScript, `load` first waits for the frames rendered before it to
report their GPU errors, and throws the first one, as
[`Renderer::render`](/api/core/renderer#render) describes.

### Renderer::read_storage \{#read_storage\}

Round-trip the GPU-side bytes of a [`Shader`](/api/core/shader)'s
storage binding back to the CPU. Submits any pending uploads, copies the
storage buffer into a pooled readback staging buffer, maps it, and returns
the bytes.

This is the only way to observe what a compute pass *wrote* into a storage
binding. [`Shader::get`](/api/core/shader) returns
what was last set on the CPU side, so GPU writes don't show up through it.

`read_storage` is `async` because the underlying `map_async` requires an
awaited callback. It returns a Promise in JS, is `async` in Swift and
`suspend` in Kotlin, and blocks until the bytes arrive in Python. On native
the implementation drives the device forward (`device.poll(Wait)`) before
awaiting, so callers don't have to spin their own poll loop. On Web the
browser schedules the callback; the helper just awaits.

Returns `RendererError::StorageBindingNotFound` when the shader does not
declare a storage binding called `binding`, or when no render pass has yet
materialized the GPU-side buffer (storage buffers are allocated lazily on
first bind).

In JavaScript, `readStorage` waits for the frames rendered before it to
report their GPU errors and throws the first one, as
[`Renderer::render`](/api/core/renderer#render)
describes. An error throws only once, so when another call, such as the next
`render`, has already thrown it, `readStorage` returns the bytes the failed
frame left behind.

#### Example

<Tabs>

<TabItem label="Rust">
<Code

### Renderer::read_texture(texture_id) \{#read_texture\}

Read back the mip-0 contents of a registered texture as tightly-packed bytes in the texture's native format.

- Works on native and on the web; the call awaits the GPU readback mapping.
- Equivalent to calling [`Texture::get_image`] on the texture handle. Use this entry point when you only kept the `TextureId` around.
- The texture must have `COPY_SRC` usage. Creation helpers like `create_storage_texture` enable it by default.
- GLES and WebGL2 can't copy a depth texture to a buffer, so reading one back there returns `TextureError::Readback`. So does a texture whose readback needs a buffer past the device's largest, `max_buffer_size`.

- In JavaScript, `readTexture` first waits for the frames rendered before it to report their GPU errors and throws the first one, as [`Renderer::render`](/api/core/renderer#render) describes.

### Renderer::render(renderable, target) \{#render\}

Renders the given object to the given [Target](/api/targets/target).

`renderable` can be a `Shader`, a `Pass`, a `Mesh`, a `Scene`, or any iterable of `Pass` (`Vec<Pass>`, `&[Pass]`, `&[&Pass]`). Passes in an iterable are rendered in order.

A window that is hidden or minimized has no frame to draw on. `render` then returns `RendererError::SurfaceError(SurfaceError::Occluded)`, which Python raises as `OccludedSurfaceError`, a `FragmentColorError`. Skip that frame and draw the next one.

A shader that reads `@location` vertex inputs needs a mesh. Without one, `render` returns `ShaderError::InvalidKey` naming the input. The inputs are the `@location` arguments of the vertex entry point and the `@location` members of its struct arguments, and each one reads the mesh attribute of its own name.

Before it takes a frame, `render` checks each shader against the device and each texture uniform against its slot, so every language returns these errors from the call that caused them, the web included. A group, binding, binding count or buffer size past the device's limits returns `RendererError::BindGroupLayoutError`, and so does a texture uniform with no texture or with a texture its slot can't take. A texture `unregister_texture` removed, or one from another `Renderer`, returns `RendererError::TextureNotFoundError`, in a PBR map slot too. A render shader without its vertex or fragment entry point returns `ShaderError::ParseError`. A compute shader on a device without compute, a workgroup past the device's limits, and anything else the device's shader validator refuses return `RendererError::Error`. The [Shader](/api/core/shader) page lists the checks.

A `Renderer` draws only into the targets it created. A target from another `Renderer` returns `RendererError::ForeignTarget`, unless every pass is a compute pass, which draws into no target. Each pass is checked against what it draws into before it records: a [depth target](/api/core/pass#set_depth_target) of the color attachment's size and sample count, shader outputs and blending the [target](/api/core/pass#set_target)'s format takes, a [viewport](/api/core/pass#set_viewport) and a [compute dispatch](/api/core/pass#set_compute_dispatch) the device takes, and textures that one pass doesn't both write and read. A render pass can't bind a texture it draws into, and no pass can read a texture one of its bindings writes, so a compute dispatch that samples a texture and stores into it returns `PassError::TextureConflict` too.

`render` also returns what the GPU rejects. When a pipeline fails to build or a frame's commands fail, it returns a [DeviceError](/api/core/deviceerror), `RendererError::DeviceError` in Rust. Its `kind` tells validation errors, internal errors such as a shader the backend compiler refuses, and running out of memory apart, and its `label` names the step that failed: the render pipeline, the compute pipeline, the light binning pipeline, the frame, or a bind group or texture view inside the frame. When one error causes another, `render` returns the first. In Rust, Python, Swift and Kotlin, a pipeline that failed is never kept, and the next frame builds it again and returns the same error.

A frame that fails is still presented. wgpu clears an image that no valid command drew into, so after a GPU error the window usually shows a cleared frame. On Apple GPUs the renderer submits the commands recorded so far before each compute pass that follows another compute pass. When a pass after that point fails, what the earlier passes drew stays on the image. A shader without its mesh, an instance count past the mesh's instances, a shader or texture the device checks refuse, a target from another `Renderer`, a pass target that is missing, and a pass whose own target or compute dispatch fails its checks fail before `render` takes a frame, and the window keeps its last image.

JavaScript gets the GPU's errors late, because WebGPU reports them after `render` has returned. Each error logs a `console.error` when it lands, and the next `render` still throws the first one, as an `Error` with `kind`, `label` and `detail` properties, before doing any work. `load`, `readTexture`, `readStorage`, and `getImage` on a `Texture` or `TextureTarget` wait for the frames before them to report, so they throw a frame's error even when called right after it. A call that waits throws only the error of a frame rendered before it began: the error of a frame rendered while it waits stays for the next call. Only the first error to land throws, and only once; the ones that land after it, before a call takes it, only log. The label names the render pipeline, the compute pipeline, the light binning pipeline or the frame. A pipeline that failed stays in the cache until its error lands, and a frame that draws with it before then reports a frame error. Once the error lands, the pipeline leaves the cache. In a loop that renders each frame, the next `render` throws the error before doing any work, and the one after it builds the pipeline again and reports the same error.

### Renderer::unregister_texture(id) \{#unregister_texture\}
