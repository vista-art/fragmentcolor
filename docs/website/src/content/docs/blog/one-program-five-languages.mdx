FragmentColor is one GPU library in five languages: Rust, JavaScript, Python, Swift, and Kotlin. Version 0.12.6 makes that sentence precise. A program reads the same in each language, with a short written list of the ways it may differ, and every example in the documentation passes its tests in all five before a release ships. Swift runs on an iOS simulator. Kotlin runs on an Android emulator.

The website shows it on the first screen. [fragmentcolor.org](/) opens on a playground where the shader rebuilds as you type and every demo appears as the same program in each language.

This post is about those two ideas and the reasons behind their shape. The [0.12.6 changelog](/blog/announcing-v0-12-6/) lists every fix.

## The same program, five times

The first demo is Cells: Worley noise, warped by fractal noise and colored with a cosine palette. Its `main.js` is the program the page runs. Beside it, the Rust, Python, Swift, and Kotlin tabs hold that program written against each binding. This is what the playground writes for Cells, unedited. Pick a language here and every other sample on this page switches with it.

<Tabs syncKey="lang">
<TabItem label="Rust">

```rust title="main.rs"
use std::error::Error;

use fragmentcolor::{Renderer, Shader, Target};

const SOURCE: &str = include_str!("shader.wgsl");

// Add a `fn main` that opens a window,
// then calls setup once and frame on every redraw.
fn setup() -> Result<Shader, Box<dyn Error>> {
    let shader = Shader::new(["noise/worley2", "noise/fbm2", "gradient/palette_iq", SOURCE])?;
    shader.set("u.scale", 12.0)?;
    shader.set("u.warp", 1.4)?;
    shader.set("u.edge", 0.08)?;
    shader.set("u.edge_color", [0.05, 0.03, 0.08])?;
    Ok(shader)
}

fn frame(
    shader: &Shader,
    renderer: &Renderer,
    target: &impl Target,
    time: f32,
    size: [f32; 2],
    pointer: [f32; 2],
) -> Result<(), Box<dyn Error>> {
    shader.set("u.time", time)?;
    shader.set("u.resolution", size)?;
    shader.set("u.mouse", pointer)?;
    renderer.render(shader, target)?;
    Ok(())
}
```

Each file has two functions. `setup` builds the shader from three library functions plus `shader.wgsl`, then sets four uniforms by name. `frame` runs on every redraw. It hands the shader the time, the canvas size, and the pointer, then renders.

The differences between tabs are the ones each language asks for. Rust and Python name methods in snake_case, and the other three use camelCase. Rust returns a `Result` that `?` passes up, Swift marks every call that can throw with `try`, and Kotlin writes its float literals as `12.0f`. The uniform keys, the library names, and the order of the calls stay put.

One difference has a reason worth spelling out. JavaScript builds the shader with `Shader.fetch`, which loads the library functions from fragmentcolor.org over the network. Native builds carry the library inside the binary, and `Shader::new` resolves the same names offline.

## Every example is a test

Every public method in FragmentColor has an entry in the [API reference](/api/core/shader/), and every entry has an example. The example starts as Rust. The build translates it into JavaScript, Python, Swift, and Kotlin, and the page shows all five in tabs.

Through 0.12.5, a Swift or Kotlin translation passed if it compiled. In 0.12.6, each one runs as a test of its own: an XCTest on an iOS simulator and a JUnit test on an Android emulator, each named after the documentation page its example came from. Rust compiles every example as a doctest and runs all but a handful, Python runs them against the built wheel, and JavaScript runs them in a browser. That makes over 170 examples per language.

Each run has to finish cleanly, which also rules out quiet GPU errors. A GPU program can fail without throwing, when wgpu reports a validation error that no code catches. The iOS, Android, and Python runs fail on any such error, and the browser run fails on any console error.

A GPU library needs that bar, since a compiler vouches for little of what happens on the GPU. Take the example for [`Pass.require`](/api/core/pass#require), which says that one pass renders after another and builds a render graph out of those links:

<Tabs syncKey="lang">
<TabItem label="Rust">

```rust
use fragmentcolor::{Pass, Renderer};
let renderer = Renderer::new();
let target = renderer.create_texture_target([100,100]).await?;
let color = Pass::new("color");
let blurx = Pass::new("blur_x");
blurx.require(&color)?; // color before blur_x
let blury = Pass::new("blur_y");
blury.require(&blurx)?; // blur_x before blur_y
let compose = Pass::new("compose");
compose.require(&color)?;
compose.require(&blury)?; // fan-in; color and blur_y before compose
renderer.render(&compose, &target)?; // compose renders last
```

This code compiled in Swift and Kotlin. When it ran, both failed with `DuplicateDependency: color`. In 0.12.6, `require` links each dependency once on both platforms, and on the web when you pass it a list.

Raw pixels hit a similar bug on both mobile platforms. Swift's `createTexture(pixels, size)` decoded the pixels as an encoded image, and the Kotlin examples that build a texture from pixels compiled, then handed them to the image decoder and failed. In 0.12.6, Swift's overload builds the texture from the pixels, and Kotlin gains the same call as `createTexture(pixels, listOf(w, h))`.

The examples on the API pages come from the same translated files these tests run. The Swift you copy from a page is the Swift that runs on a simulator before each release ships.

## What "looks the same" means

"The same API in five languages" is easy to say and hard to keep. Bindings drift a little with every release unless someone writes down where they may differ. FragmentColor writes it down as a short list of accepted differences. Anything outside the list counts as a bug, and the release that finds it fixes it in all five bindings.

Names come first. Methods follow each language's case, and constructors follow its idiom. Named constructors such as `Pass::from_shader` and `Shader::fetch` are static methods everywhere.

| Language | Method | Constructor |
| --- | --- | --- |
| Rust | `create_texture` | `Shader::new(source)` |
| JavaScript | `createTexture` | `new Shader(source)` |
| Python | `create_texture` | `Shader(source)` |
| Swift | `createTexture` | `Shader(source)` |
| Kotlin | `createTexture` | `Shader(source)` |

Calls that wait or fail take each language's own form, and so does a value that may be missing.

| Language | Async call | Error | Missing value |
| --- | --- | --- | --- |
| Rust | `async fn` | `Result` | `None` |
| JavaScript | Promise | thrown `Error` | `undefined` |
| Python | blocks | `FragmentColorError` | `None` |
| Swift | `async` | `FragmentColorError` | `nil` |
| Kotlin | `suspend` | `FragmentColorException` | `null` |

Numbers and bytes arrive in each language's native types.

| Language | Unsigned integer | Bytes |
| --- | --- | --- |
| Rust | `u32`, `u64` | `&[u8]` |
| JavaScript | number, throws if negative | `Uint8Array`, `ArrayBuffer` |
| Python | `int`, raises if negative | `bytes`, `bytearray`, `memoryview`, uint8 ndarray |
| Swift | `UInt32`, `UInt64` | `Data`, `[UInt8]` |
| Kotlin | `UInt`, `ULong` | `ByteArray` |

Type names match everywhere. `WindowTarget`, `TextureTarget`, and `TextureRegion` are the same classes in Rust, JavaScript, Python, Swift, and Kotlin. The older names that only one binding used, such as `CanvasTarget`, `RenderCanvasTarget`, and `TextureRegionMobile`, remain as aliases.

Return values match as well. A Rust method that returns its receiver returns it in every binding, which lets `scene.add(model).add(camera)` chain. A size comes back as a `Size`, and in Python `texture.size.width` returns the width. Value types such as `Size`, `ScreenRegion`, and `TextureFormat` compare by value in Python, Swift, and Kotlin.

Four differences take the most getting used to: async calls, errors, unsigned integers, and tuple arguments. Each gets an example below.

### Async, and the bytes that come back

[`get_image`](/api/targets/texturetarget#get_image) reads a target back into memory:

The read is async in Rust and returns a Promise in JavaScript. Swift awaits it with `await` alone, because the method doesn't throw. Kotlin declares it `suspend`, and you call it from a coroutine. Python blocks until the bytes arrive. Every binding has the method, under the same name in its own case.

The bytes agree too: RGBA8, rows from top to bottom, without padding. Python returns them as a NumPy array shaped `(height, width, 4)` and indexed `image[y, x]`, the layout NumPy, OpenCV, and pygfx read. `create_texture` reads that layout as well, and `renderer.create_texture(target.get_image())` uploads the same image. Python's `TextureTarget.get_image` returned the transpose before 0.12.6. Code that indexed it `[x, y]` now indexes `[y, x]`.

### Errors that look like errors

A Rust `Result` turns into the error each language expects. JavaScript throws `Error` objects, and `e.message` carries the text, where most methods used to throw bare strings. Python raises `FragmentColorError` or one of its subclasses, and `TypeError` when an argument has the wrong type. Swift throws `FragmentColorError`. Kotlin throws `FragmentColorException`, argument errors included, where those used to surface as `IllegalArgumentException`.

The rule covers bad input too, which several bindings used to absorb without a word. JavaScript clamped or zeroed sizes it could not use, and an index of `-1` wrapped around to `4294967295`. The old `Int` overloads in Swift and Kotlin trapped on negative numbers or wrapped them. On the web, `new Shader(source)` with broken WGSL returned the red fallback shader that `Shader.default()` still gives.

In 0.12.6, bad input fails where you can see it. JavaScript and Python reject a size, region, or byte value they can't use, unsigned types keep negatives out of Swift and Kotlin, `new Shader` throws, and `Shader.fetch` rejects.

Uniforms follow one set of rules in all five languages. [`Shader.set`](/api/core/shader#set) reads a value against the type the shader declares. An integer uniform takes whole numbers in range, a vector takes exactly as many numbers as it has components, and a `mat2x2`, `mat3x3`, or `mat4x4` takes 4, 9, or 16. Give a `vec2<f32>` three numbers and the error names the problem: `resolution: expected vec2<f32>, got 3 number(s)`.

Vertex and instance attributes take their type the same way, when the mesh attaches to a shader. With `@location(1) id: u32` in the shader, [`vertex.set("id", 7)`](/api/geometry/vertex#set) uploads a `u32` in every language, and a `-1` fails the attach with `Mesh attribute id: expected u32, got -1 at vertex 0`.

A live editor depends on errors like these. When an edit breaks the shader, the constructor throws, the playground prints the message under the editor, and the last shader that built keeps drawing.

Where Rust takes a `u32` or `u64`, such as an index, a count, a size, or a region, Swift takes `UInt32` or `UInt64` and Kotlin takes `UInt` or `ULong`. A negative value never reaches the library, because the compiler stops it first. Swift literals fit as written, as in `pass.setComputeDispatch(64, 64, 1)`. Kotlin marks them with a `u`: `64u`, or `listOf(64u, 64u)` for a size.

Of all the changes in 0.12.6, this one is the most likely to touch existing Swift and Kotlin code. An `Int` variable no longer compiles where an unsigned value belongs. Check its sign, then convert it with `UInt32(n)` in Swift or `n.toUInt()` in Kotlin. JavaScript and Python take plain numbers, and a negative one throws in JavaScript and raises in Python. Byte lists are the exception: Swift also takes `[Int]` and Kotlin `List<Int>`, with each value between 0 and 255.

### Tuples become arguments

Some Rust methods take a single tuple, because they accept anything that converts into one input type. The bindings spread that tuple into ordinary arguments, and trailing optional parts can be left out. Each language keeps its own forms. The size is a `[w, h]` list everywhere, written `listOf(64u, 64u)` in Kotlin. The format is `TextureFormat::Rgba` in Rust, `TextureFormat.Rgba` in JavaScript and Python, `TextureFormat.rgba` in Swift, and `TextureFormat.RGBA` in Kotlin. The bytes come in each language's own list type, and Swift's `[Int]` is the byte-list exception from the section above. Python names the optional part with `data=`.

## The playground on the home page

The playground fills the home page, and `/demos` redirects there. Every demo is WGSL plus a `main.js`, and both are yours to edit. Most keep their WGSL in one `shader.wgsl`. Particles splits its compute and render shaders into two files, and Life keeps one file for each of its four passes. The playground rebuilds the program a quarter second after you stop typing.

`main.js` exports two functions. `setup(renderer, target)` runs once per build and returns whatever the program keeps between frames. `frame(state, renderer, target, time, size, pointer)` runs on every animation frame. The imports use plain Vite syntax, as in `import SOURCE from "./shader.wgsl?raw"`, and the file runs unchanged in a Vite project.

### Controls from the shader

The sliders under the canvas come from the shader itself. The playground lists its keys with [`listKeys`](/api/core/shader#list_keys), reads each value with [`get`](/api/core/shader#get), and skips the keys that `frame` sets on every frame. A `// min..max` comment on a struct field sets the slider's range. This is the uniform block from Cells:

```wgsl
struct Params {
  resolution: vec2<f32>,
  mouse: vec2<f32>,
  time: f32,
  scale: f32, // 2..24
  warp: f32, // 0..3
  edge: f32, // 0.01..0.4
  edge_color: vec3<f32>,
}

@group(0) @binding(0) var<uniform> u: Params;
```

`scale`, `warp`, and `edge` become sliders with the ranges in their comments. `edge_color` is a `vec3` with `color` in its name, and it gets a color picker. `resolution`, `mouse`, and `time` change on every frame and get no control.

The code takes input too. Click a number and a slider appears beside it. A color literal such as `vec3<f32>(0.55, 0.5, 0.48)` gets a swatch that opens a color picker. On a `shader.set` value in `main.js`, the inline slider and the generated control move together without a rebuild, and moving the generated control rewrites the value in the code.

### The library bar

The **Library** bar edits the `const LIBRARY = [...]` line in `main.js`. Each entry names a function from the [shader library](/shaders/), and `Shader.fetch` loads those functions ahead of your WGSL. Your shader can call `worley2` or `heart` without defining it.

### Compute, and six artworks

Two demos run compute shaders. In Particles, one million particles live in a storage buffer. A compute pass moves them and an instanced render pass draws them, and both shaders share the buffer by its name.

Life runs four passes over a million particles of four species, and each species follows or flees the density of the others. Three compute passes turn the particles counted per grid cell into density slopes, clear the grid, and move each particle along the slopes while `atomicAdd` counts it into its new cell. A fourth pass draws the result. Both demos need WebGPU, and a browser that draws with WebGL2 shows a recording while the code stays editable.

## Fixes you can see

Most of 0.12.6 is repair work, and the [changelog](/blog/announcing-v0-12-6/) lists all of it. The two compute demos depend on several of those fixes.

Life needs 0.12.6 to run at all. Version 0.12.5 rejected the `atomic<u32>` storage buffers it counts with, and every pass in one `render` call drew with the last pass's uniform values. In 0.12.6, storage buffers hold `atomic<u32>` and `atomic<i32>`, and each pass keeps its own uniforms.

The memory fixes matter most at a million particles. A simulation that size leaked about 30 MB each time it rebuilt, and at eight million particles every frame copied about 256 MB of storage buffers to the GPU. FragmentColor now frees passes, shaders, and their storage buffers when the last handle drops, and a storage buffer uploads only when it is created, resized, or changed by `set`. A `render` made only of compute passes acquires no surface frame, and a simulation keeps running while its window is minimized.

Two library shapes draw correctly now. [`sdf2d/heart`](/shaders/sdf2d/#heart) returns Inigo Quilez's exact signed distance, and outlines and glows trace the heart. [`pattern/hexgrid`](/shaders/pattern/#hexgrid) draws hexagons where it drew tall, overlapping cells.

## Upgrading

The sections above cover the changes most likely to touch existing code: JavaScript `Error` objects, `new Shader` throwing on the web, unsigned integers in Swift and Kotlin, and Python's `[y, x]` image layout. Two more are worth a look:

- A `ScreenRegion` built from `[w, h]` covers exactly that size. It used to add a pixel on each side.
- Rust drops items that were public by accident, the glam conversions among them. Pass `v.to_array()` where code passed a glam vector.

<Aside type="caution" title="Swift Package Manager">
Each release tag pins its own xcframework. A dependency on `from: "0.12.5"` received the 0.12.4 binary, and the Swift wrapper the package compiled predated 0.12.0, without `Scene`, `Model`, and the other [0.12 types](/blog/announcing-v0-12-0/). Move Swift dependencies to 0.12.6.
</Aside>

The [complete list](/blog/announcing-v0-12-6/#breaking-and-behavior-changes) covers every change and what to do about it.
