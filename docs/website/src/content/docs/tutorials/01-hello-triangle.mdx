There's a rite of passage in graphics programming:  **Drawing your first triangle.**

**This typically takes thousands of lines of code.** Pick any tutorial for OpenGL, Vulkan, or raw WebGPU, and you'll spend an afternoon setting pixel formats, allocating command pools, and wiring descriptor sets & binding groups before any colored pixel reaches the screen.

**We're going to do it in 5 lines of <Lang/>**.

</Lock>

## Step 1: Hello, triangle!

To draw anything, anywhere, we need two things:

- a **surface** to draw on,
- and **something that draws**.

In FragmentColor those are a `Target` and a `Renderer`. Let's create them:

<MultiCode
  rust={`let renderer = Renderer::new();
let target = renderer.create_target(canvas).await?;`}
  js={`const renderer = new Renderer();
const target = await renderer.createTarget(canvas);`}
  py={`renderer = Renderer()
target = renderer.create_target(canvas)`}
  swift={`let renderer = Renderer()
let target = try renderer.createTarget(canvas)`}
  kotlin={`val renderer = Renderer()
val target = renderer.createTarget(canvas)`}
/>

The `canvas` is whatever your platform draws into: a `<canvas>` element on the web, an `Arc<Window>` from `winit` in Rust, a `RenderCanvas` in Python, a `CAMetalLayer` on iOS and a `Surface` on Android. In every case, the `Renderer` wraps it in a `Target`.

Now, what do we draw? A **`Shader`**: a small program that runs on the GPU, the graphics chip in your computer or phone. Drawing takes two stages. The **vertex** stage runs once per corner of a shape and decides where that corner lands on the screen. Every pixel inside the shape then gets one run of the **fragment** stage, which picks its color. FragmentColor takes its name from that second stage.

**Congratulations! That's your first triangle!** Click the four numbers in the code to pick another color.

Behind those five lines of <Lang />, FragmentColor validates the WGSL and compiles it for your GPU. It builds a render pipeline, creates a buffer for `color` and copies your four numbers into it. Then it records the draw and submits it.

The shader, from the top:

- `var<uniform> color: vec4<f32>` declares a **uniform**, a value the program sets from outside the shader. Its type, `vec4<f32>`, is four 32-bit floats, here red, green, blue and alpha. FragmentColor reads the declaration from the source and finds the uniform by its name, which is how `set("color", ...)` knows where the numbers go. The `@group(0) @binding(0)` in front is WGSL bookkeeping: no two bindings in one shader may share the same pair of numbers.
- `vs_main` is the vertex stage. A shader with no geometry attached draws three vertices, so `vs_main` runs three times. Its argument `i`, marked `@builtin(vertex_index)`, tells each run which corner to compute. The corners are in **normalized device coordinates**: `x` goes from -1 on the left edge to 1 on the right, `y` from -1 at the bottom to 1 at the top, whatever the target's size in pixels.
- `VOut` carries the result in `pos`, the field marked `@builtin(position)`. After `x` and `y` come a depth for sorting overlapping shapes and a divisor for perspective. A flat drawing leaves them at `0.0` and `1.0`.
- `fs_main`, the fragment stage, returns `color` for every pixel the triangle covers. `@location(0)` on its result sends that color to the target.

### Make it move

One call to `render` draws one frame. To animate, we update the uniform and render again, over and over. Each step of this tutorial splits its code into two functions. `setup` runs once and builds the shader. On every display refresh, `frame` receives `time`, the seconds since the animation started, and draws.

In JavaScript, a loop like this one plays a step on a `<canvas>`:

```js
import init, { Renderer } from "fragmentcolor";
import { setup, frame } from "./example.js";

await init();
const renderer = new Renderer();
const target = await renderer.createTarget(canvas);
const state = await setup(renderer);

let start;
requestAnimationFrame(function draw(milliseconds) {
  start ??= milliseconds;
  frame(state, renderer, target, (milliseconds - start) / 1000);
  requestAnimationFrame(draw);
});
```

## Step 2: A second uniform

Our corners describe a triangle with three equal sides. On a wide screen, the demo above draws it short and broad.

Normalized device coordinates run from -1 to 1 across the full width and, separately, across the full height. When the canvas is wider than it is tall, one unit along `x` spans more pixels than one unit along `y`. A phone held upright flips that: its canvas is taller than it is wide, which pulls the triangle into a thin spike.

The shader needs the canvas size to undo that stretch. A second uniform carries it:

<Snippet file="01-hello-triangle/02-resolution-uniform/example.rs" region="shader" />

`resolution` holds the target's width and height in pixels. The vertex stage divides one by the other to get the aspect ratio, then scales positions down along the longer axis to match the shorter one. One unit now covers the same number of pixels in both directions.

On the program side, `frame` reads the target's size and sets it next to the color:

<Snippet file="01-hello-triangle/02-resolution-uniform/example.rs" region="frame" />

<Demo file="01-hello-triangle/02-resolution-uniform/example.rs" />

Three equal sides, on any canvas. From here on, every shader that draws our triangle declares `resolution`. Each `frame` sets it before rendering.

## Step 3: The shader library

The `Shader` constructor also takes a list. Each entry can be WGSL source, a path to a `.wgsl` file or the name of a function in FragmentColor's [shader library](/shaders/). FragmentColor joins the entries in order and compiles them as one program.

More than 200 small WGSL functions make up the library: easing curves, color spaces, hashes, noise, distance functions in 2D and 3D, lighting models and post-processing effects. Each name pairs a category with a function, such as `noise/simplex2`. Rust, Python, Swift and Kotlin ship the whole library inside the package and look names up offline. On the web, a name means a download, and a constructor can't wait for one: JavaScript loads such a list with `await Shader.fetch(...)`, while a list of plain WGSL still works with `new Shader(...)`.

Here `noise/simplex2` goes first in the list, ahead of our triangle's source:

<Snippet file="01-hello-triangle/03-compose-noise/example.rs" region="setup" />

Our fragment stage can now call `simplex2` as if we had written it ourselves. Three other things are new in this shader:

- A third uniform, `time`. `frame` sets it on every refresh, along with `color`.
- `uv`, a second field in `VOut`. For each corner, the vertex stage computes a pair of numbers between 0 and 1, a common way to label points on a surface. The GPU blends the three pairs across the triangle, giving each run of `fs_main` its own mix. The `@location` numbers name the slots that pass values from the vertex stage to the fragment stage. Each `@location` field of `VOut` takes a different number.
- `.rgb` and `.a`, which pick channels out of a vector: `color.rgb` is the first three numbers of `color`, and `color.a` is the fourth.

<Snippet file="01-hello-triangle/03-compose-noise/example.rs" region="shader" />

<Snippet file="01-hello-triangle/03-compose-noise/example.rs" region="frame" />

Simplex noise gives a smooth, random-looking value for every point in the plane. The fragment stage samples it at each pixel's `uv` and slides that point as `time` grows. Each value scales the color between 55% and full brightness. Soft patches of light drift across the triangle like sunlight through leaves on a windy day.

## Step 4: Bring your own vertices

So far the corners have lived inside the shader. Most programs keep their geometry on the CPU and send it to the GPU. FragmentColor gives them two objects for that:

- **`Vertex`** is one point. Its constructor takes the position, and `set` attaches any other attribute by name, such as a color, a normal or texture coordinates.
- **`Mesh`** is a list of vertices.

We build three vertices, each with its own color, and attach the mesh to the shader:

<Snippet file="01-hello-triangle/04-vertex-gradient/example.rs" region="setup" />

Each position has a third number, `z`, for depth. Our flat triangle sets it to `0.0`.

The vertex stage now declares two inputs, `position` at `@location(0)` and `color` at `@location(1)`. On a vertex input, `@location` refers to an attribute slot. Attribute slots have a numbering of their own, apart from the one in `VOut`. When we call <code><Lang rust="add_mesh" js="addMesh" py="add_mesh" swift="addMesh" kotlin="addMesh" /></code>, FragmentColor matches the vertices' positions and `color` attributes to those inputs by name. If the mesh has nothing for an input the shader reads, the call fails with an error that names it.

<Snippet file="01-hello-triangle/04-vertex-gradient/example.rs" region="shader" />

`position.xy` keeps the first two numbers of `position` and drops `z`.

<Demo file="01-hello-triangle/04-vertex-gradient/example.rs" />

Pink, green and blue sit at the three corners. The GPU blends the vertex colors as it blends `uv` in step 3: a pixel near the pink corner comes out mostly pink, while one in the middle gets equal parts of all three. Our program only ever sets the corners.

## Step 5: Fifteen thousand triangles

One triangle is a warm-up. **Let's draw 15,000.**

The mesh from step 4 is all we need: the GPU repeats it 15,000 times, each copy with its own spot, phase and tint. Those copies are **instances**. An **`Instance`** holds the attributes of one copy, as a `Vertex` holds the attributes of one corner. Graphics programmers call small things drawn in large numbers **particles**. So does our code.

<Snippet file="01-hello-triangle/05-instances/example.rs" region="setup" />

`position` and `color` change from corner to corner. `center`, `phase` and `tint` belong to an `Instance`: all three corners of a copy use the same ones.

<Snippet file="01-hello-triangle/05-instances/example.rs" region="shader" />

Each copy traces a small curve around its `center`. `phase` gives every copy a head start along its sine waves, which spreads their peaks across time. The library's `easing/in_out_sine` shapes the brightness. It flattens the wave at its top and bottom: each triangle holds its brightest and dimmest moments a little longer.

## Step 6: A post-processing pass

For a change of pace, let's make it look like film. We render the particles into a texture first, then draw that texture to the canvas through a second shader, which grades the picture with four functions from the library:

- `postfx/chromatic_offsets` returns three slightly different spots to read red, green and blue from, like a cheap lens that splits colors near its edges.
- `color/tonemap_filmic` compresses the highlights toward white along a curve from Jim Hejl and Richard Burgess-Dawson. The shader halves the brightness before the curve so the colors don't wash out.
- `postfx/vignette` darkens the corners.
- `postfx/film_grain` adds a new layer of noise on every frame.

Two more objects hand the picture from the first shader to the second:

- **`Texture`** is an image stored on the GPU. A `TextureTarget` keeps what we draw into it as a `Texture` that another shader can read.
- **`Pass`** groups shaders and draws them into one target. `render` can take a bare `Shader`, as in the steps before. A `Pass` adds a target of its own, a clear color and an order among passes. Its name labels the pass in GPU errors and debuggers.

## Step 7: A million triangles

Step 5 builds every `Instance` on the CPU with its own `set` calls, then uploads them all. Fifteen thousand copies make a short loop. A million would make a long one. The GPU can invent the numbers itself.

<Snippet file="01-hello-triangle/07-instance-index/example.rs" region="setup" />

A vertex that has only a position can go in as a bare list of numbers. Two numbers per vertex are enough for a flat shape. <code><Lang rust="set_instance_count" js="setInstanceCount" py="set_instance_count" swift="setInstanceCount" kotlin="setInstanceCount" /></code> asks for a million copies of the mesh without a single `Instance`. `hash` scrambles a number, and `random` maps the result to a value between 0 and 1. Because an index always hashes to the same values, each triangle keeps its spot from one frame to the next. Four values per copy pick a distance from the center, one of three arms, a sideways scatter and a brightness, each from its own seed: the index times four, plus 0 to 3. Three pieces of WGSL need explaining:

- `u32` is a 32-bit whole number that is never negative. A `u` after a literal, as in `4u`, makes it one.
- Angles are in radians, where a full turn is `6.283`. `2.094` is a third of a turn, one arm's share.
- `mix(core, rim, radius)` blends from `core` to `rim` as `radius` goes from 0 to 1.

Two lines replace step 2's aspect fix. `fit` divides the shorter side by each side of the canvas: 1 for the short axis, less for the long one. The second line, `position * 6.0 / resolution`, sizes the triangle in pixels instead. With two units across the canvas, one pixel is `2.0 / resolution` units wide. Each triangle comes out about four pixels across.

### Your frame budget

A display shows a new picture on every refresh. The time between two refreshes is the **frame budget**: 1000 milliseconds divided by the refresh rate, about 16.7 ms at 60 Hz and 8.3 ms at 120 Hz. Your display settings list the rate. In a browser, the gap between `requestAnimationFrame` callbacks tells you the same thing. Paste this into the console:

```js
const stamps = [];
await new Promise((done) => requestAnimationFrame(function tick(now) {
  stamps.push(now);
  if (now - stamps[0] < 1000) requestAnimationFrame(tick);
  else done();
}));
const gap = (stamps.at(-1) - stamps[0]) / (stamps.length - 1);
console.log(`${Math.round(1000 / gap)} frames a second, ${gap.toFixed(1)} ms apart`);
```

With nothing playing, it prints your refresh rate. Run it again while the demo above plays to see how often the page manages a new frame. Once the work stops fitting in the budget, the gap widens to two refreshes or more.

A timestamp around `renderer.render` measures only the CPU side. `render` records the work and submits it to the GPU, which finishes later. To time the GPU from Rust, render a batch of frames, wait for the last one by reading its pixels back, and divide the elapsed time by how many there were. `host.rs` does that whenever you set `FC_TUTORIAL_FRAMES`: `FC_TUTORIAL_FRAMES=120 ./fc example tutorial_01_hello_triangle_instance_index` renders 120 of them offscreen at 1280 × 720 and prints the average. A browser's performance panel shows the same work on its GPU track.

Each GPU's **crossover point** is the count where the frame time grows past your budget. To find yours, change `COPIES` at the top of the step's file and measure again: with the command above in Rust, or with the console snippet while your copy of `example.js` plays.

**The demo draws a million triangles. Your GPU decides whether all of them fit in your budget.**

Twice the triangles take about twice as long to draw. Shrinking each one to a tenth of its width cuts the frame time by less than half. At four pixels wide, the count sets the length of a frame.

## What just happened

Seven steps, eight objects. Here's what each one does:

- **`Renderer`** draws. Every `frame` ends in a call to `render`.
- **`Target`** receives the picture: a window or canvas in every step, plus a texture in step 6.
- **`Shader`** is the program the GPU runs. It gets a uniform in step 1 and library functions in steps 3, 5 and 6.
- **`Vertex`** and **`Mesh`** (step 4) move the geometry out of the shader and into our program.
- **`Instance`** gives one triangle 15,000 copies in step 5. Step 7 drops it for a count and an index.
- **`Pass`** chains shaders: two render passes with a **`Texture`** between them in step 6.
