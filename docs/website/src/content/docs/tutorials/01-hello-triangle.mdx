There's a rite of passage in graphics programming:  **Drawing your first triangle.**

**This typically takes thousands of lines of code.** Pick any tutorial for OpenGL, Vulkan, or raw WebGPU, and you'll spend an afternoon setting pixel formats, allocating command pools, and wiring descriptor sets & binding groups before any colored pixel reaches the screen.

**We're going to do it in 5 lines of <Lang/>**.

</Lock>

## Step 1: Hello, triangle!

To draw anything, anywhere, we need two things:

- a **surface** to draw on,
- and **something that draws**.

In FragmentColor those are a `Target` and a `Renderer`. Let's create them:

<MultiCode
  rust={`// canvas is an Arc<Window> from winit
let renderer = Renderer::new();
let target = renderer.create_target(canvas).await?;`}
  js={`// canvas is a <canvas> element
const renderer = new Renderer();
const target = await renderer.createTarget(canvas);`}
  py={`# canvas is a RenderCanvas from rendercanvas
renderer = Renderer()
target = renderer.create_target(canvas)`}
  swift={`// canvas is a CAMetalLayer, such as an MTKView's layer
let renderer = Renderer()
let target = try renderer.createTarget(canvas)`}
  kotlin={`// canvas is an android.view.Surface, such as a SurfaceView's
val renderer = Renderer()
val target = renderer.createTarget(canvas)`}
/>

The `canvas` is whatever your platform draws into: a `<canvas>` element on the web, a winit window in Rust, a `RenderCanvas` in Python, a `CAMetalLayer` on iOS and macOS, and a `Surface` on Android. The `Renderer` wraps it in a `Target`.

Now, what do we draw? That's the job of a **`Shader`**, a small program the GPU runs in two stages. The vertex stage decides where each corner of the triangle lands on the screen. The fragment stage decides the color of every pixel inside it. Shaders are written in WGSL, the shading language of WebGPU, and here is ours:

<Snippet file="01-hello-triangle/01-three-lines/example.rs" region="shader" />

Keep that source in a string called `TRIANGLE`. Three more lines turn it into a picture:

<ColorTriangle />

Congratulations! You just drew your first triangle! Click the color in the code to pick another one.

That's five lines of <Lang />, and none of them mentions a pipeline. FragmentColor validated the WGSL, compiled it for your GPU, built a render pipeline, created a buffer for `color` and copied your four numbers into it, then recorded the draw and sent it to the GPU.

Let's read the shader from the top:

- `var<uniform> color: vec4<f32>` declares a **uniform**, a value the program sets from outside the shader. `vec4<f32>` means four 32-bit floats: red, green, blue and alpha. FragmentColor reads this declaration from the source, which is how `set("color", ...)` knows where the four numbers go.
- `vs_main` is the vertex stage. A shader with no geometry attached draws three vertices, so `vs_main` runs three times, and `vertex_index` tells each run which corner it computes. The corners are in normalized device coordinates, where `x` and `y` run from -1 to 1 across the target, whatever its size in pixels.
- `fs_main` is the fragment stage. It runs once for every pixel the triangle covers and returns `color`.

The triangle covers about a fifth of the canvas. On a 1920 × 1080 screen that's some 435,000 pixels, and the GPU runs `fs_main` for all of them in parallel.

### Make it move

One call to `render` draws one frame. To animate, we set the uniform and render again every time the screen refreshes. Each step of this tutorial splits its code the same way: a `setup` function that runs once, and a `frame` function that runs on every refresh, about 60 times a second. Its `time` argument holds the seconds since the program started.

## Step 2: A second uniform

Make your browser window narrower while the demo above runs, then wider again.

The triangle stretches with the canvas. Normalized device coordinates map -1 to 1 onto each axis separately. On a canvas twice as wide as it is tall, one unit along `x` spans twice as many pixels as one unit along `y`, and our equilateral triangle comes out wide and flat.

The shader can't correct for a shape it doesn't know. A second uniform tells it:

<Snippet file="01-hello-triangle/02-resolution-uniform/example.rs" region="shader" />

`resolution` holds the target's width and height in pixels. The vertex stage divides one by the other to get the aspect ratio, then shrinks the longer axis until one unit covers the same number of pixels in both directions.

On the program side, `frame` reads the target's size and sets it next to the color:

<Snippet file="01-hello-triangle/02-resolution-uniform/example.rs" region="frame" />

<Demo file="01-hello-triangle/02-resolution-uniform/example.rs" />

Resize the window again. The triangle holds its shape. Every shader from here on declares `resolution`, and every `frame` sets it before it renders.

## Step 3: Borrow from the shader library

The `Shader` constructor also takes a list. Each entry can be WGSL source, a path to a `.wgsl` file, a URL, or the name of a function in FragmentColor's [shader library](/shaders/). FragmentColor joins the entries in order and compiles them as one program. An entry that appears twice goes in once.

The library holds more than 200 small WGSL functions: easing curves, color spaces, hashes, noise, distance functions in 2D and 3D, lighting models and post-processing effects. Each one has a name made of a category and a function, such as `noise/simplex2`. Here it goes in front of our triangle:

<Snippet file="01-hello-triangle/03-compose-noise/example.rs" region="setup" />

On the web, a constructor can't wait for a download, so JavaScript loads a list with `await Shader.fetch(...)`. The other languages ship the whole library inside the package and look the names up offline.

Our fragment stage can now call `simplex2` as if we had written it ourselves:

<Snippet file="01-hello-triangle/03-compose-noise/example.rs" region="shader" />

Simplex noise gives a smooth, random-looking value for every point in the plane. The fragment stage samples it across the triangle, slides the samples along with `time`, and uses the result to dim and brighten the color. The surface ripples like heat haze over asphalt.

<Demo file="01-hello-triangle/03-compose-noise/example.rs" />

## Step 4: Bring your own vertices

So far the corners have lived inside the shader. Most programs keep their geometry on the CPU and hand it to the GPU, and FragmentColor gives them two objects for that:

- **`Vertex`** is one point. It holds a position and any attributes we attach with `set`, such as a color, texture coordinates or a normal.
- **`Mesh`** is a list of vertices.

We build three vertices, each with its own color, and attach the mesh to the shader:

<Snippet file="01-hello-triangle/04-vertex-gradient/example.rs" region="setup" />

The vertex stage now declares two inputs, `position` at `@location(0)` and `color` at `@location(1)`. When we call `add_mesh`, FragmentColor matches the vertex attributes to those inputs by name and checks every vertex. A missing attribute fails right there, with an error that names it. Plain numbers take the type the shader declares, which makes each `color` a `vec3<f32>`.

<Snippet file="01-hello-triangle/04-vertex-gradient/example.rs" region="shader" />

<Demo file="01-hello-triangle/04-vertex-gradient/example.rs" />

Pink, green and blue sit at the three corners, and every pixel between them mixes the three. We never wrote any blending code. The vertex stage hands `color` to the fragment stage, and the GPU interpolates it on the way: a pixel near the pink corner gets mostly pink, and a pixel in the middle gets an even mix.

## Step 5: Fifteen thousand triangles

One triangle is nice. Let's draw fifteen thousand.

We don't need fifteen thousand meshes. We need one mesh drawn fifteen thousand times, each copy with its own place, phase and tint. Those copies are **instances**, and an **`Instance`** holds the attributes of one copy the way a `Vertex` holds the attributes of one corner:

<Snippet file="01-hello-triangle/05-particle-trail/example.rs" region="setup" />

The vertex stage reads both kinds of input. `position` and `color` change from corner to corner. `center`, `phase` and `tint` change from copy to copy and stay the same for all three corners of a copy. FragmentColor matches each input by name and knows which attributes belong to instances.

<Snippet file="01-hello-triangle/05-particle-trail/example.rs" region="shader" />

`easing/in_out_sine` comes from the library this time. It reshapes a wave that runs from 0 to 1, and each triangle lingers at its brightest and its dimmest while it hurries through the middle.

On every frame the program sends two values, `time` and `resolution`, and the vertex stage moves all fifteen thousand triangles from them:

<Snippet file="01-hello-triangle/05-particle-trail/example.rs" region="frame" />

<Demo file="01-hello-triangle/05-particle-trail/example.rs" />

That's 45,000 vertices per frame, drawn with a single draw call.

## Step 6: A post-processing pass

For the last step, let's make it look like film. We render the triangles into a texture first, then draw that texture to the screen through a second shader. The second shader grades the picture with four functions from the library:

- `postfx/chromatic_offsets` returns three slightly different spots to read red, green and blue from, the way a cheap lens splits colors near its edges.
- `color/tonemap_filmic` rolls off bright highlights along a curve by Jim Hejl and Richard Burgess-Dawson that mimics film.
- `postfx/vignette` darkens the corners.
- `postfx/film_grain` adds a new layer of noise on every frame.

Two more objects make this possible:

- **`Pass`** runs its shaders into one target.
- **`Texture`** is an image on the GPU. A texture target keeps what it renders in a `Texture`, and another shader can read it.

<Snippet file="01-hello-triangle/06-postfx-pass/example.rs" region="setup" />

`set_target` points the particle pass at the texture. `require` tells the output pass that the particle pass has to run first. Now `frame` asks the renderer for the output pass alone, and the renderer runs everything that pass requires before it:

<Snippet file="01-hello-triangle/06-postfx-pass/example.rs" region="frame" />

The postfx shader covers the screen with one oversized triangle and reads the particle texture under every pixel:

<Snippet file="01-hello-triangle/06-postfx-pass/example.rs" region="postfx-shader" />

<Demo file="01-hello-triangle/06-postfx-pass/example.rs" />

The particle shader is the one from step 5, line for line. It renders into a square texture, and the postfx shader stretches that square across the canvas. The particle shader still squeezes its triangles by the canvas's aspect ratio, and the stretch undoes the squeeze.

## What just happened

In six steps we used every object in FragmentColor's core:

- **`Renderer`** draws. Every step ends in the same `render` call.
- **`Target`** is where the drawing lands: a window or canvas in every step, and a texture in step 6.
- **`Shader`** is the program the GPU runs. It took its first uniform in step 1 and borrowed from the shader library in steps 3, 5 and 6.
- **`Vertex`** and **`Mesh`** moved the geometry into our program in step 4.
- **`Instance`** turned one triangle into fifteen thousand in step 5.
- **`Pass`** and **`Texture`** chained two shaders in step 6, the first drawing into a texture and the second reading from it.

Compute shaders use the same objects. A `Shader` with a `@compute` entry point goes into a `Pass` and runs through the same `render` call.
