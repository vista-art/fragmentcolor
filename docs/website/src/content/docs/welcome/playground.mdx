## How it works

Every demo is a WGSL shader and a `main.js` that drives it. Both are yours to edit. The playground rebuilds the program a quarter second after you stop typing. When a build fails, the error shows under the editor and the last version that built keeps drawing.

`main.js` exports two functions. `setup(renderer, target)` runs once per build and returns whatever the program keeps between frames. `frame(state, renderer, target, time, size, pointer)` runs on every animation frame. The imports are plain Vite syntax (`import SOURCE from "./shader.wgsl?raw"`), so the file runs unchanged in a Vite project.

The **Library** bar edits the `const LIBRARY = [...]` line in `main.js`. Each entry names a function from the [shader library](/shaders/), and [`Shader.fetch`](/api/core/shader/) loads those functions ahead of your WGSL, so the shader can call `worley2` or `heart` without defining it.

The sliders come from the shader itself. The playground lists its keys with [`listKeys`](/api/core/shader/), reads each value with [`get`](/api/core/shader/), and leaves out the keys `frame` sets on every frame. A `// min..max` comment on a struct field sets the slider range, and a `vec3` or `vec4` field whose name contains `color` gets a color picker.

The **Artworks** group holds six longer shaders built from the library. The pointer steers them as it does the other demos, and their `press`, `pulse`, `drag`, and `zoom` uniforms are sliders.

The Rust, Python, Swift, and Kotlin tabs show the same program written against each binding. They follow the library, the shader files, and the current slider values. Edit the WGSL or `main.js` to change them.
